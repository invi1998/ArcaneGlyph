# Unreal Engine 5 (UE5) 中的委托系统

委托是 UE 中实现事件驱动编程和解耦的核心机制，理解其类型、绑定方式和注意事项对于编写健壮、高效的代码至关重要。

**核心概念回顾：**
委托本质上是一个类型安全的函数指针容器（对于多播）或包装器（对于单播）。它允许你将一个或多个函数（或可调用对象）“订阅”到一个事件或通知上。当事件触发时（委托被“广播”或“执行”），所有绑定的函数都会被调用。这实现了对象间的松耦合通信：触发者不需要知道具体的接收者是谁，只需要知道委托签名（函数参数和返回类型）。

---

## 一、 UE5 委托的主要类型

UE5 的委托系统主要分为三大类，每类又有其特点和适用场景：

1.  **单播委托 (`DECLARE_DELEGATE` 系列)**
    *   **核心特性：** 只能绑定 **一个** 函数或可调用对象。尝试绑定第二个会替换掉第一个。
    *   **主要用途：**
        *   回调函数（Callback）：例如异步操作完成后的通知（资源加载、网络请求）。
        *   需要确切知道只有一个响应者的情况。
        *   需要返回值的情况（单播委托可以有返回值，最后一个绑定的函数返回值会被返回）。
    *   **常见变体：**
        *   `DECLARE_DELEGATE(DelegateName)`：无参数。
        *   `DECLARE_DELEGATE_OneParam(DelegateName, Param1Type)`：一个参数。
        *   `DECLARE_DELEGATE_TwoParams(DelegateName, Param1Type, Param2Type)`：两个参数。
        *   `DECLARE_DELEGATE_RetVal(RetValType, DelegateName)`：有返回值，无参数。
        *   `DECLARE_DELEGATE_RetVal_OneParam(RetValType, DelegateName, Param1Type)`：有返回值，一个参数。
        *   ... (最多支持 9 个参数的各种组合)。
    *   **执行：** 使用 `Execute()` 或 `ExecuteIfBound()` 方法执行。`ExecuteIfBound()` 更安全，只在有绑定函数时才执行。

2.  **多播委托 (`DECLARE_MULTICAST_DELEGATE` 系列)**
    *   **核心特性：** 可以绑定 **多个** 函数或可调用对象。当委托广播时，所有绑定的函数会按照绑定顺序被调用。
    *   **主要用途：**
        *   事件通知系统：游戏中大量使用（`Actor` 的 `OnDestroyed`, `OnActorBeginOverlap`, `OnComponentHit` 等都是多播委托）。
        *   观察者模式（Observer Pattern）：一个主题（Subject）通知多个观察者（Observers）。
        *   不需要返回值的情况（多播委托通常声明为 `void` 返回类型）。
    *   **常见变体：**
        *   `DECLARE_MULTICAST_DELEGATE(DelegateName)`
        *   `DECLARE_MULTICAST_DELEGATE_OneParam(DelegateName, Param1Type)`
        *   `DECLARE_MULTICAST_DELEGATE_TwoParams(DelegateName, Param1Type, Param2Type)`
        *   ... (最多支持 9 个参数)。
    *   **执行：** 使用 `Broadcast()` 方法触发所有绑定的函数。通常没有返回值（或返回值被忽略）。

3.  **动态委托 (`DECLARE_DYNAMIC_DELEGATE` 和 `DECLARE_DYNAMIC_MULTICAST_DELEGATE` 系列)**
    *   **核心特性：**
        *   **序列化支持：** 可以被 Blueprint 使用，其绑定关系可以保存到磁盘（序列化）。这是它们与普通单播/多播委托最根本的区别。
        *   **反射依赖：** 依赖于 UE 的反射系统 (Unreal Header Tool - UHT)。委托签名和绑定的 UFUNCTION 必须被 UHT 识别。
        *   **性能开销：** 由于反射和序列化支持，执行速度通常比非动态委托慢。
        *   **参数限制：** 参数类型必须是 UObject 指针、基本数据类型（`int32`, `float`, `bool`, `FString`, `FText`, `FName`）或支持蓝图的其他类型（结构体需要标记为 `BlueprintType` 且成员也需支持）。**不支持模板类型、裸指针（非 UObject*）或复杂 C++ 类型。**
    *   **主要用途：**
        *   **暴露给蓝图：** 这是最主要的目的！允许 C++ 类定义事件，蓝图可以实现这些事件（绑定到蓝图函数）或绑定蓝图函数到这些委托。
        *   **需要跨会话保存的绑定：** 例如关卡蓝图中的事件绑定。
    *   **类型：**
        *   **动态单播委托 (`DECLARE_DYNAMIC_DELEGATE[_...]`):** 理论上可以绑定一个蓝图函数，但实际中**极少使用**。蓝图无法方便地绑定到单播委托（因为只能有一个绑定）。
        *   **动态多播委托 (`DECLARE_DYNAMIC_MULTICAST_DELEGATE[_...]`):** **最常用的动态委托类型。** 在 C++ 中声明为事件，蓝图可以添加/移除多个绑定。在蓝图中显示为带有“+”图标的可分配事件。
    *   **执行：** 动态多播委托使用 `Broadcast()`。动态单播委托使用 `Execute()` 或 `ExecuteIfBound()`。
    *   **绑定要求 (C++ 侧)：** 绑定的 C++ 函数必须是 `UFUNCTION()`，并且其参数和返回类型必须与委托签名严格兼容（考虑 UHT 支持的类型）。

## 二、 委托绑定方式详解

绑定是指将具体的函数、Lambda 表达式或其他可调用对象关联到委托实例上的操作。UE 提供了多种灵活的绑定方式，各有其优缺点和适用场景。

### 通用步骤 (声明与定义)
1.  **声明：** 在类定义（通常是头文件 `.h`）中使用上述 `DECLARE_...` 宏声明委托类型。
    ```cpp
    // MyClass.h
    DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(FMyDamageEventDelegate, float, DamageAmount); // 动态多播委托示例
    DECLARE_MULTICAST_DELEGATE(FMySimpleEventDelegate); // 普通多播委托示例
    DECLARE_DELEGATE_RetVal(bool, FMyCheckDelegate); // 普通单播委托（带返回值）示例
    ```
2.  **定义成员变量：** 在类中声明该委托类型的公共或私有成员变量。
    ```cpp
    // MyClass.h
    public:
        UPROPERTY(BlueprintAssignable, Category = "My Events") // BlueprintAssignable 对动态多播委托至关重要
        FMyDamageEventDelegate OnDamageTaken;
        FMySimpleEventDelegate OnSomethingHappened;
        FMyCheckDelegate OnCanPerformAction;
    ```
3.  **绑定：** 在代码（通常是 `.cpp` 文件）中，在适当的时机（如 `BeginPlay`, 构造函数后，或响应其他事件时）将函数绑定到委托实例。
4.  **执行/广播：** 在需要触发事件的地方调用 `Execute()`, `ExecuteIfBound()` (单播) 或 `Broadcast()` (多播)。

### 具体绑定方法

1.  **绑定到 UObject 的成员函数 (`BindUObject`, `AddUObject`):**
    *   **方法：**
        *   单播: `DelegateInstance.BindUObject(ObjectPointer, &UMyClass::MemberFunction);`
        *   多播: `DelegateInstance.AddUObject(ObjectPointer, &UMyClass::MemberFunction);`
        *   动态多播 (C++ 绑定): `DelegateInstance.AddDynamic(ObjectPointer, &UMyClass::UFUNCTION_MemberFunction);` (注意：必须用 `&UClass::FunctionName` 语法且函数是 `UFUNCTION`)
    *   **适用：** 最常用、最安全的方式之一。用于绑定到 `UObject` 派生类实例的成员函数。
    *   **注意事项：**
        *   **生命周期管理（关键！）：** 委托内部持有对 `ObjectPointer` 的**弱引用**。如果对象被垃圾回收（GC）或手动 `delete` 了，委托调用将**不会**执行（避免了野指针崩溃）。这是其最大的安全性优势。
        *   `AddDynamic` **要求**绑定的函数必须是 `UFUNCTION()`，且参数匹配动态委托支持的类型。
        *   确保 `ObjectPointer` 在绑定时刻是有效的（非 `nullptr`）。
        *   **解绑：** 使用返回的 `FDelegateHandle` (调用 `Remove` 或 `RemoveAll` 时) 或让对象在销毁时自动解绑（弱引用机制本身防止了崩溃，但最好显式解绑以清理资源）。

2.  **绑定到共享指针指向对象的成员函数 (`BindSP`, `AddSP`):**
    *   **方法：**
        *   单播: `DelegateInstance.BindSP(SharedPointer, &FMySharedPtrClass::MemberFunction);`
        *   多播: `DelegateInstance.AddSP(SharedPointer, &FMySharedPtrClass::MemberFunction);`
    *   **适用：** 绑定到由 `TSharedPtr` 或 `TSharedRef` 管理的非 `UObject` 对象的成员函数。
    *   **注意事项：**
        *   **生命周期管理：** 委托内部持有对共享指针的**强引用**。只要委托存在，绑定的对象就不会被销毁。这确保了对象在委托调用时存活，但**可能导致对象生命周期意外延长（内存泄漏风险）**。仔细考虑这是否符合你的需求。
        *   确保 `SharedPointer` 有效。
        *   **解绑：** 同样需要使用 `FDelegateHandle` 显式解绑。解绑后强引用被释放。

3.  **绑定到原始 C++ 对象指针的成员函数 (`BindRaw`, `AddRaw`):**
    *   **方法：**
        *   单播: `DelegateInstance.BindRaw(RawObjectPointer, &FMyRawClass::MemberFunction);`
        *   多播: `DelegateInstance.AddRaw(RawObjectPointer, &FMyRawClass::MemberFunction);`
    *   **适用：** 绑定到不由 UE 垃圾回收管理，也不由智能指针管理的普通 C++ 对象（例如，引擎子系统、自定义管理器）。
    *   **注意事项：**
        *   **生命周期管理（高风险！）：** 委托内部**只存储裸指针**。**开发者必须 100% 确保 `RawObjectPointer` 在委托可能被调用的整个生命周期内有效，并且在对象销毁前显式解绑所有与其相关的委托。** 违反此规则会导致野指针访问和程序崩溃。**极其谨慎使用！**
        *   通常仅用于生命周期非常明确且长于委托的对象（如单例或游戏模式）。
        *   **解绑：** **绝对必须**使用 `FDelegateHandle` 在对象销毁前显式解绑。

4.  **绑定到静态函数 (`BindStatic`, `AddStatic`):**
    *   **方法：**
        *   单播: `DelegateInstance.BindStatic(&MyStaticFunction);`
        *   多播: `DelegateInstance.AddStatic(&MyStaticFunction);`
    *   **适用：** 绑定到全局函数或类的静态成员函数。静态函数没有 `this` 指针。
    *   **注意事项：**
        *   **生命周期：** 静态函数始终存在，无需担心对象生命周期。
        *   **访问限制：** 静态函数无法直接访问非静态的类成员变量（因为没有 `this` 指针）。如果需要访问特定对象状态，通常需要将对象指针作为参数传递给委托（通过委托签名），或者考虑其他绑定方式（如 `BindUObject`）。
        *   通常用于工具函数、库函数或不需要特定对象实例上下文的操作。

5.  **绑定到 Lambda 表达式 (`BindLambda`, `AddLambda`):**
    *   **方法：**
        *   单播: `DelegateInstance.BindLambda([](Params...) { /* Lambda Body */ });`
        *   多播: `DelegateInstance.AddLambda([](Params...) { /* Lambda Body */ });`
    *   **适用：** 非常灵活的方式，适合一次性或简单的内联逻辑。可以捕获上下文变量。
    *   **注意事项：**
        *   **生命周期管理（捕获变量）：** 这是最大的陷阱！
            *   **值捕获 (`[=]`, `[var]`):** Lambda 持有变量的拷贝。安全，但如果拷贝开销大（如大型结构体、容器）或你需要修改原变量，需注意。
            *   **引用捕获 (`[&]`, `[&var]`):** Lambda 持有变量的引用。**极度危险！** 你必须确保被引用的变量在 Lambda 被调用时**依然存在**且**在其原始作用域内有效**。如果捕获了局部变量而该作用域已结束，或捕获的对象指针已被销毁，调用 Lambda 将导致崩溃或未定义行为。**仅在 Lambda 生命周期非常短（例如，在同一个函数栈帧内立即执行）且你能完全控制捕获变量生命周期时使用引用捕获。**
            *   **捕获 `this` (`[this]`):** 类似于 `BindRaw`。Lambda 持有 `this` 裸指针。**你必须确保该对象在 Lambda 被调用时依然存活！** 如果对象是 `UObject`，强烈建议改用 `BindUObject` 或捕获 `TWeakObjectPtr`。
            *   **捕获智能指针 (`[SharedThis]`):** 如果对象由 `TSharedPtr` 管理，按值捕获 `SharedThis` 会延长对象生命周期（强引用）。按引用捕获 (`[&SharedThis]`) 同样危险。
        *   **推荐做法：**
            *   优先考虑值捕获，特别是对于基本类型和小型 POD 结构体。
            *   对于需要访问 `UObject` 成员，**强烈推荐**在 Lambda 中捕获 `TWeakObjectPtr`，并在 Lambda 内部检查其有效性：
                ```cpp
                TWeakObjectPtr MyWeakPtr = MyUObject;
                Delegate.AddLambda([MyWeakPtr](Params...) {
                    if (UMyObject* Obj = MyWeakPtr.Get()) {
                        // 安全访问 Obj 的成员
                    }
                });
                ```
            *   避免在可能长时间存在的委托中使用引用捕获局部变量。
            *   明确写出捕获列表 (`[var1, &var2, this]`) 而不是笼统的 `[=]` 或 `[&]`，提高可读性和安全性。
        *   **性能：** Lambda 通常能很好地被编译器内联，性能良好。

6.  **绑定到 Functor (函数对象) (`BindUObject`, `BindSP`, `BindRaw` 等也可用于重载了 `operator()` 的对象):**
    *   **方法：** 与绑定成员函数类似，但传递的是函数对象实例的指针/引用，以及指向 `operator()` 的成员函数指针。`BindLambda` 本质上也是一种创建临时 Functor 的语法糖。
    *   **适用：** 需要携带复杂状态的函数对象。
    *   **注意事项：** 生命周期管理规则取决于你使用的具体绑定宏（`BindUObject`, `BindSP`, `BindRaw`），与绑定成员函数相同。需确保函数对象本身的生命周期。

7.  **蓝图绑定 (仅限动态委托 - 主要是动态多播委托):**
    *   **方法：**
        *   **C++ -> 蓝图 (事件):** 在 C++ 中声明一个 `BlueprintAssignable` 的动态多播委托成员变量 (`UPROPERTY`)。在蓝图中，找到该组件或对象的该委托变量，点击其右边的 "+" 图标（或在图表中右键 -> "Assign [DelegateName]"），然后选择或创建一个自定义事件节点来实现逻辑。
        *   **蓝图 -> C++ (函数):** 在 C++ 中将一个 `UFUNCTION(BlueprintCallable)` 函数的参数定义为动态委托类型（通常是动态单播委托，尽管少见）。在蓝图中调用这个 C++ 函数时，可以将一个蓝图函数（匹配委托签名）作为参数传递进去，本质上就是绑定。更常见的模式是蓝图绑定到 C++ 定义的事件（上一种情况）。
    *   **注意事项：**
        *   只适用于动态委托（`DECLARE_DYNAMIC_...`）。
        *   绑定在蓝图中完成，序列化保存。
        *   蓝图绑定的函数自动满足动态委托的参数类型限制。
        *   生命周期由 UE 的蓝图实例和关卡流管理控制。

### 解绑
*   **单播委托：** 直接调用 `Unbind()`。通常在你需要替换绑定或确定不再需要回调时调用。
*   **多播委托：**
    *   所有 `Add...` 方法 (`AddUObject`, `AddStatic`, `AddLambda`, `AddDynamic` 等) 都会返回一个 `FDelegateHandle`。
    *   使用 `DelegateInstance.Remove(DelegateHandle)` 移除特定的绑定。
    *   使用 `DelegateInstance.RemoveAll(ObjectPointer)` 移除所有绑定到特定对象（`UObject*` 或原始指针）上的函数。这非常有用，通常在对象（如 `AActor`）的 `EndPlay` 或析构函数中调用，以确保对象销毁后委托不再尝试调用它。
    *   使用 `DelegateInstance.Clear()` 移除所有绑定。
*   **动态委托 (蓝图绑定)：** 解绑通常在蓝图中通过断开事件节点的连接线完成。C++ 端也可以使用 `RemoveAll(ObjectPointer)` 来移除特定对象的所有绑定（包括蓝图绑定到该对象的函数）。

## 三、 绑定时的注意事项与最佳实践总结

1.  **生命周期管理是核心挑战：**
    *   **首要原则：** 确保当委托执行时，被绑定的函数所依赖的对象和它访问的所有数据仍然有效。
    *   **优先选择安全机制：**
        *   对于 `UObject`: **首选 `BindUObject` / `AddUObject` / `AddDynamic`。** 依赖其内置的弱引用机制，防止野指针崩溃。
        *   对于需要访问 `UObject` 的 Lambda: **捕获 `TWeakObjectPtr` 并在 Lambda 内检查 `IsValid()` / `Get()`。**
        *   对于 `TSharedPtr` 对象: **理解 `BindSP` / `AddSP` 会创建强引用并延长对象生命周期。** 确保这是期望的行为，避免循环引用导致泄漏。必要时使用 `TWeakPtr` 并在 Lambda 内提升。
    *   **极度警惕：**
        *   `BindRaw` / `AddRaw`: 仅在对象生命周期绝对长于委托且你能手动管理解绑时使用。
        *   Lambda 引用捕获 (`[&]`): 仅在 Lambda 立即执行或你能完全保证被引用的局部变量/临时对象在调用点绝对存活时使用。
        *   在 Lambda 中捕获 `this` (`[this]`): 等同于 `BindRaw`，风险很高。优先用 `BindUObject` 或 `TWeakObjectPtr`。
    *   **解绑责任：** 当一个对象（尤其是 `AActor` 或 `UActorComponent`）不再需要接收委托通知或即将被销毁时，**必须主动解绑**它绑定的所有委托（使用 `RemoveAll(this)` 是最常见和可靠的方式）。不要依赖委托的弱引用作为不解绑的借口，解绑是清理资源和避免无效操作的必要步骤。

2.  **执行前检查绑定状态：**
    *   **单播：** 总是优先使用 `ExecuteIfBound()` 而不是 `Execute()`。`ExecuteIfBound()` 安全地检查是否有绑定。
    *   **多播：** `Broadcast()` 内部会检查绑定列表是否为空，可以安全调用。但如果你想优化（避免不必要的广播开销），可以先用 `IsBound()` 检查（但这通常不是瓶颈）。

3.  **多播委托广播期间的绑定修改：**
    *   在 `Broadcast()` 执行期间遍历绑定列表时，**不要在该遍历过程中添加或移除绑定**。这可能导致迭代器失效（崩溃）或不可预期的行为（新绑定可能在同一轮广播中被调用或错过）。
    *   如果需要修改绑定列表，一种常见模式是先在广播时收集需要添加/移除的操作，然后在广播结束后再执行这些操作。

4.  **动态委托的限制：**
    *   **参数类型：** 牢记动态委托参数必须是蓝图可识别的类型（`UObject*`, 基本类型，`BlueprintType` 结构体）。不要尝试绑定带有限制类型参数的函数。
    *   **UFUNCTION：** 使用 `AddDynamic` 绑定的 C++ 函数**必须**标记为 `UFUNCTION()`。
    *   **性能：** 避免在性能敏感的循环或每帧逻辑中使用大量的动态委托广播。

5.  **委托签名匹配：**
    *   绑定的函数（包括 Lambda）其参数数量、类型、顺序以及返回类型（对于单播）必须与委托声明**完全匹配**。编译器会捕获大部分错误。

6.  **Lambda 捕获的谨慎使用：**
    *   明确写出捕获列表。
    *   优先按值捕获小型数据或需要快照的数据。
    *   **绝对避免**在可能长期存在的委托中捕获局部变量的引用 (`[&]`)。
    *   访问 `UObject` 时，**强制使用 `TWeakObjectPtr`**。
    *   注意 Lambda 本身的复制开销（如果委托是按值传递的）。

7.  **线程安全：**
    *   UE 的委托系统本身**不是线程安全的**。委托的绑定、解绑和执行通常都应在游戏线程（主线程）上进行。
    *   如果需要在其他线程触发事件，常见的模式是将事件参数封装到一个结构体里，通过线程安全的队列（如 `TQueue`）发送到游戏线程，然后在游戏线程上安全地广播委托。不要在其他线程直接调用 `Broadcast()` 或 `Execute()`。

8.  **性能考量：**
    *   委托调用本身有开销（虚函数调用或函数指针调用），但通常可以接受。
    *   大量（数千）绑定的多播委托广播可能成为瓶颈，需评估。
    *   简单的 Lambda 通常能被内联，性能较好。复杂的成员函数调用或虚拟函数调用开销更大。
    *   动态委托由于涉及反射，比普通委托慢。

9.  **选择正确的委托类型：**
    *   **需要暴露给蓝图？** -> **必须**用动态多播委托 (`DECLARE_DYNAMIC_MULTICAST_DELEGATE...`)。
    *   **需要多个响应者？** -> 用多播委托 (`DECLARE_MULTICAST_DELEGATE...`)。
    *   **只需要一个响应者或需要返回值？** -> 用单播委托 (`DECLARE_DELEGATE...`)。
    *   **纯粹 C++ 内部高性能事件？** -> 优先用普通单播/多播委托。
    *   **回调函数？** -> 单播委托 (`BindUObject`, `BindStatic`, `BindLambda` 等)。

10. **`FDelegateHandle` 的重要性：**
    *   对于多播委托的任何绑定（除了蓝图绑定的解绑在蓝图侧），**务必保存** `Add...` 方法返回的 `FDelegateHandle`。
    *   这是后续安全解绑特定绑定的**唯一可靠方式**。不要依赖对象指针来解绑单个绑定（`RemoveAll(Object)` 会移除该对象的所有绑定）。
    *   通常将 `FDelegateHandle` 作为绑定该委托的类（通常是订阅者）的成员变量存储。

## 四、 什么情况下用什么，不可以用什么？(快速参考)

| 场景/需求                                  | 推荐委托类型与绑定方式                                       | 不推荐/禁止                                                  | 关键注意事项                                                 |
| :----------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **暴露事件给蓝图**                         | **动态多播委托 (`DECLARE_DYNAMIC_MULTICAST_DELEGATE`)** + `UPROPERTY(BlueprintAssignable)` | 普通单播/多播委托、动态单播委托                              | 参数类型必须支持蓝图                                         |
| **蓝图函数绑定到 C++ 委托参数**            | C++ 函数参数定义为**动态（单播）委托** + `UFUNCTION(BlueprintCallable)` | 普通委托                                                     | 较少见，通常用事件更好                                       |
| **UObject 成员函数作为回调 (C++)**         | **单播：`BindUObject`** <br> **多播：`AddUObject`**          | `BindRaw` / `AddRaw` (危险), Lambda 直接捕获 `this` (危险)   | **首选安全方式！** 利用弱引用。记得在对象销毁时 `RemoveAll(this)` 或解绑 `FDelegateHandle`。 |
| **UObject 成员函数作为事件处理 (C++)**     | **多播：`AddUObject`**                                       | `AddRaw` (危险)                                              | 同上。                                                       |
| **在 Lambda 中访问 UObject (C++)**         | **Lambda 捕获 `TWeakObjectPtr` + 内部 `Get()` 检查**         | Lambda 直接捕获 `UObject*` 或 `[this]` (危险), `AddRaw` (危险) | **强制使用弱指针检查！**                                     |
| **绑定静态函数/全局函数 (C++)**            | **`BindStatic` / `AddStatic`**                               | -                                                            | 静态函数无法访问非静态成员。                                 |
| **绑定到 `TSharedPtr` 管理对象的成员函数** | **`BindSP` / `AddSP`** (理解强引用!) <br> 或 捕获 `TWeakPtr` + 提升 (Lambda) | `BindRaw` / `AddRaw` (危险)                                  | `BindSP` 会延长对象生命周期，可能导致循环引用泄漏。`TWeakPtr` 更安全但需检查。 |
| **绑定到原始 C++ 对象指针成员函数**        | **仅当对象生命周期绝对长于委托且你能手动解绑时：`BindRaw` / `AddRaw`** | **默认不推荐！** 高风险。                                    | **你必须 100% 保证对象存活并在销毁前显式解绑！** 首选重构为 `UObject` 或智能指针管理。 |
| **简单内联逻辑 (C++)**                     | **`BindLambda` / `AddLambda`**                               | 专门写一个成员函数或静态函数 (如果逻辑非常简单，Lambda 更简洁) | **小心捕获！** 避免引用捕获局部变量。访问 UObject 用 `TWeakObjectPtr`。 |
| **需要返回值**                             | **单播委托 (`DECLARE_DELEGATE_RetVal...`)**                  | 多播委托 (无返回值或返回值被忽略)                            | 只有最后绑定的函数返回值有效。                               |
| **高频、性能关键路径事件 (C++)**           | **普通单播/多播委托** + **`BindUObject` / `BindStatic` / `BindLambda` (简单)** | 动态委托 (反射开销), 复杂的绑定函数 (虚函数、大型捕获 Lambda) | 优化绑定函数逻辑和减少绑定数量。                             |
| **对象即将销毁**                           | **在其 `EndPlay` / `BeginDestroy` / 析构函数中调用 `OnMyDelegate.RemoveAll(this);`** | 不解绑 (可能导致委托尝试调用已销毁对象，即使 `BindUObject` 弱引用安全，但解绑是良好实践并避免无效操作) | **必须做！**                                                 |
| **跨线程触发事件**                         | **将事件参数打包，通过线程安全队列发送到游戏线程，在游戏线程广播委托** | **禁止在其他线程直接调用 `Broadcast()` / `Execute()`!**      | 委托系统本身非线程安全。                                     |
| **动态委托参数**                           | **仅限 UObject*, 基本类型 (int, float, bool), FString, FName, FText, BlueprintType 结构体** | 模板类型、裸指针 (非 UObject*)、复杂 C++ 类型 (STL 容器)、引用 (`&` - 蓝图用值传递) | 编译错误或运行时序列化失败。                                 |

---

**总结:**

UE5 的委托系统强大而灵活，是解耦和事件驱动的基石。**深入理解不同类型委托的特点（单播 vs 多播 vs 动态），熟练掌握各种绑定方式（特别是 `BindUObject`/`AddUObject`/`AddDynamic` 和安全的 Lambda 捕获 `TWeakObjectPtr`），并时刻警惕生命周期管理问题，是编写健壮 UE 代码的关键。** 牢记“优先安全绑定方式”、“绑定必有解绑”、“动态委托有类型限制”、“警惕 Lambda 捕获陷阱”和“委托非线程安全”这些核心原则，就能有效地利用委托构建清晰、可维护的游戏逻辑。务必根据具体场景选择最合适的委托类型和绑定策略。
